Why teams need it

The standard connection turns every alert into a new ticket.

SAP Cloud ALM can create ServiceNow incidents out of the box, one call per event. That works in a small landscape. In a real one, the service desk soon stops trusting the feed.

Duplicates

One business problem fires many monitoring events, and each one opens its own incident.

Tickets that never close

Interface and IDoc monitoring report errors but never send an "all clear", so incidents stay open until someone closes them by hand.

Wrong team, wrong priority

The same template is used for a database alert, a failed IDoc and a stuck integration message, so routing and severity are fixed after the fact.

Fragile after changes

A new tenant, a move to RISE or a new monitoring use case means reconfiguring the integration.

How it works

Four steps from a Cloud ALM alert to the right ServiceNow ticket.

The adapter sits between the two tools. Cloud ALM keeps doing the monitoring, ServiceNow keeps owning the incident. The adapter makes sure what arrives in ServiceNow is clean.

  1. 01

    Cloud ALM detects something

    A system metric crosses a threshold, an interface fails, an IDoc goes into error or a job breaks. Cloud ALM sends the event to the adapter.

  2. 02

    The adapter recognises it

    It reads which system and component the event is about and gives it a fixed identity. The tenth event about the same interface gets the same identity as the first.

  3. 03

    It applies your rules

    Each type of alert has its own rules: which assignment group, which category, which priority. A database alert goes to Basis, a failed IDoc to the integration team.

  4. 04

    ServiceNow handles the ticket

    ServiceNow Event Management groups the events, opens one incident and keeps it updated. When the problem recovers, the incident closes on its own.

SAP Cloud ALM→DIFF Adapter→ServiceNow Event Management→Incident

Questions

Frequently asked.

Do we need ServiceNow Event Management?

Yes. Event Management does the grouping, deduplication and automatic closing. If you only have ITSM, talk to us about the options.

Does it replace the SAP standard integration?

It replaces the direct alert-to-incident connection for the monitoring sources in scope. Cloud ALM and ServiceNow stay configured as you know them.

Where does it run and who owns it?

In your own SAP BTP account, on Cloud Foundry. It uses only public Cloud ALM and ServiceNow APIs and stores no data of its own.

What happens when we add a system or move to RISE?

You add or adjust a rule for that system. No code changes and no new integration project.

Can we try it first?

Yes. We start on a non-production tenant with Health Monitoring and show the result in your ServiceNow before anything goes live.
